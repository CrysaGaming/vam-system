### Schritt 2 — Navigraph-OAuth-Flow durch DevTools-Network-Tab Initiator-Chain

User triggerte Unlink+Link-Sequenz von Navigraph in vAMSYS-USER-Account-Settings (jeder User macht das einmalig für sich selbst, kein VA-Admin-Setup). Initiator-Chain dokumentiert komplett:

Browser flow:
  1. User klickt "Link Navigraph" in eigenen Account-Settings → vAMSYS-Server initiiert OAuth-Redirect
  2. GET https://identity.api.navigraph.com/connect/authorize (oder /connect/consent wenn bereits eingeloggt)
       ?client_id=vamsys-frontend
       &response_type=code
       &state=<csrf-token>
       &scope=openid+...   (vollständige scope-list im HAR)
  3. User authorisiert auf Navigraph
  4. GET https://auth.vamsys.io/user/oauth/navigraph
       ?code=<authorization-code>
       &state=<csrf-token>
       &session_state=<oidc-session>
  5. Server-side (NICHT in browser-network):
     POST https://identity.api.navigraph.com/connect/token
       Body: { code, client_id, client_secret, grant_type: 'authorization_code' }
       Response: { access_token, refresh_token, expires_in }
  6. vAMSYS speichert tokens FÜR DEN USER in User-DB-Row
  7. 302 Redirect zu /user/social (User landet zurück)

### Schritt 3 — Architektur-Modell

Standard OAuth 2.0 Authorization Code Flow mit OIDC. Navigraph akquirierte SimBrief 2021. Apps registrieren sich bei Navigraph als OAuth-Client (ONE registration per APP), bekommen client_id + client_secret. Pro-User-Authorisierung erfolgt einmalig durch jeden User. Danach kann App im Namen des Users auf SimBrief zugreifen — server-to-server, ohne Browser-Interaktion.

PER-USER-TOKEN-STORAGE: Jeder User hat eigene Tokens. Kein User kann OFPs im Namen eines anderen generieren. VA-Admins haben keinen automatischen Zugriff auf User-Navigraph-Accounts. Passt zu existierendem Multi-Tenancy-Pattern (User → Pilot → Airline) und Phase-1-Schema-Decision: simBriefUsername/simBriefStaticId sind bereits auf User-Level verortet.

## Implementation-Plan für VAM-System (Pattern Y)

### App-Registration (einmalig, pro VAM-System-Instanz)

VAM-System registriert sich bei Navigraph-Developer-Portal als OAuth-Client. Bekommt: NAVIGRAPH_CLIENT_ID + NAVIGRAPH_CLIENT_SECRET. Beides in .env. Callback-URL hinterlegt: https://vam.kevindrack.de/api/oauth/navigraph/callback

### Schema-Erweiterung (User-Model, NICHT Airline-Model)

Per-User OAuth-Tokens — jeder Pilot hat eigene:

- navigraphAccessToken: String?
- navigraphRefreshToken: String?
- navigraphTokenExpiresAt: DateTime?
- navigraphSubject: String? (OIDC subject claim, eindeutige User-ID bei Navigraph — nützlich für Re-Linking-Detection)

### Routes

- /api/oauth/navigraph/start (GET, requireUser) → redirect to identity.api.navigraph.com/connect/authorize mit state in DB-Session gespeichert
- /api/oauth/navigraph/callback (GET) → state validation, code-exchange, store tokens in current-user-row
- /api/oauth/navigraph/refresh (server-action, internal) → refresh-token-flow vor expiry

### Server-Action für Booking-Dispatch (ersetzt dispatchSimBrief)

- Server lädt Booking via requireUserWithAirline + ownership-check
- Server holt User.navigraphAccessToken (current-user)
- Wenn token expired: refresh-token-flow durchführen
- Server-side fetch zu SimBrief-API mit Bearer-Auth
- XML-Parse mit existierendem parser.ts
- Cache + Booking-Link wie bisher in captureSimBriefOfp

### UI-Surface

- User-Settings-Page: "Connect Navigraph"-Button (analog zu vAMSYS). Status-Indicator: "Connected" / "Not connected" / "Token expired". Disconnect-Action für User-Self-Service.
- Booking-Detail-Page: Dispatch-Button löst direkt Server-Action aus (kein Popup, kein Output-Page-Roundtrip). OFP rendert inline auf Booking-Page.
- Falls User noch nicht verlinkt: Inline-Hinweis + Link zu Settings.
